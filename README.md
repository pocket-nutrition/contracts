# Shared client contract

One pinnable coordinate for everything the Pocket Nutrition clients must agree on: the API schema,
the design tokens, the FR copy deck, and the shared behavioural test vectors.

- API: <https://api.pocketnutrition.org>
- Organisation: <https://github.com/pocket-nutrition>

## Purpose

`pocket-nutrition/android` and `pocket-nutrition/ios` are separate native apps. They must behave
identically without sharing a line of runtime code. This repository is how that gets enforced:
each app vendors a tagged snapshot of it, and CI fails when the vendored copy goes stale.

Without a single repository the clients would pin three independent versions (schema from `api`,
tokens from `design`, vectors from somewhere else) and someone would have to answer "which
combination is compatible?" on every release. One tag answers it by construction.

It is **MPL-2.0**, like the rest of the client tier — this repo ships inside the app binaries, so
it cannot carry the AGPL the backend uses. See "Licence" below.

## Stack

| Concern | Choice |
|---|---|
| Build | None. Committed JSON plus a few Python scripts. |
| Dependencies | PyYAML, and nothing else |
| Distribution | Git tag (`contract-vX.Y.Z`), vendored into each app repo |

## Contents

```
VERSION                        # the coordinate every consumer pins
openapi/
  openapi.upstream.json        # verbatim snapshot of /v3/api-docs — never hand-edit
  overlay.yaml                 # patch document, with a WHY per entry
  openapi.patched.json         # GENERATED + COMMITTED — the only file clients consume
scripts/
  patch_spec.py                # upstream + overlay -> patched   (--check for CI)
  check_codegen_parity.py      # compares the two GENERATED clients against the spec
tokens/                        # design tokens, semantic map, cooking palette
strings/                       # FR copy deck
vectors/                       # shared behavioural test corpus
```

## Why the upstream spec is not used directly

`openapi.upstream.json` is generated by springdoc from Kotlin annotations. Four things make it
unusable for client generation, all addressed by `overlay.yaml` + `patch_spec.py`:

| Problem | Consequence if unfixed |
|---|---|
| No `required` arrays on any schema | Every field optional in both languages, including `energyKcal`. Not a domain type but a bag of maybes, with a `?? 0` decision at every call site, in two languages, made independently |
| `X-Segment-Count` undocumented | No generator emits an accessor, so multi-select search (spec §7.1) silently disappears |
| `/health` is `@Hidden` | The apps need it to validate a user-entered server address — the core of the configurable-server feature |
| Closed enums | A shipped binary cannot learn a new value, and cannot be fixed after release |

`required` is **derived from nullability**, not hand-listed: springdoc encodes a Kotlin `Double?`
as `{"type": ["number","null"]}`, so the derivation mirrors Kotlin exactly and a newly added DTO
field is classified automatically. Hand-listing would let a field stay silently optional because
nobody updated a list living in another repository.

### The bug that justifies `check_codegen_parity.py`

Verified against swift-openapi-generator 1.13.0 and openapi-generator 7.24.0.

springdoc encodes a nullable `$ref` property as `oneOf: [{$ref: ...}, {type: null}]`.
openapi-generator understands this. **swift-openapi-generator does not** — it logs

```
warning: Schema "null" is not supported, reason: "schema type", skipping
```

and then **omits the property from the generated struct entirely**. The build succeeds.

The casualty was `IngredientSuggestionWithNutrition.nutrition` — the entire nutritional payload of
an enriched search result. Kotlin generated 17 properties, Swift 16. The iOS app would have
compiled, run, and shown no nutrition on search results, with nothing anywhere reporting a problem.

`patch_spec.py` now normalizes that form to a bare `$ref`, carrying optionality in `required`
instead, which both generators honour. `check_codegen_parity.py` is the regression guard, and it
compares *generated output* rather than the spec — because the failure mode was a generator
silently disagreeing with the spec.

Two hand-written clients would have diverged the same way, just more slowly and in more places.
That is the argument for generating them.

## Running locally

```bash
# 1. Refresh the upstream snapshot after an API contract change. The source of truth is
#    pocket-nutrition/api/contract/openapi.json, itself pinned by OpenApiSnapshotTest, so prefer
#    copying that over curling production.
cp ../api/contract/openapi.json openapi/openapi.upstream.json

# 2. Re-apply the overlay.
python3 scripts/patch_spec.py

# 3. Review the diff, then bump VERSION (minor = additive, major = breaking).
git diff openapi/

# CI equivalent
python3 scripts/patch_spec.py --check      # fails if the committed output is stale
```

`patch_spec.py` output is byte-reproducible — no timestamps, no environment-dependent values.
That is what makes `--check` trustworthy.

## Generating clients

Both commands read `openapi/openapi.patched.json`. Neither app commits the generator; both commit
the generated sources, so builds are offline and every change is a reviewable diff.

**Kotlin** (`pocket-nutrition/android`, module `:core-api`):

```bash
openapi-generator generate \
  -i contract/openapi.patched.json \
  -g kotlin -o contract/generated \
  --additional-properties=library=jvm-retrofit2,serializationLibrary=kotlinx_serialization,useCoroutines=true,enumUnknownDefaultCase=true,packageName=org.pocketnutrition.core.api.generated
```

`library=jvm-retrofit2` is deliberate: it returns `Response<T>`, which exposes `.headers()`, and is
therefore the only variant that can read `X-Segment-Count`. `enumUnknownDefaultCase=true` produces
the tolerant-reader fallback case.

**Swift** (`pocket-nutrition/ios`, target `CoreAPI`) — `apple/swift-openapi-generator` as an SPM
build plugin. SPM plugins cannot read outside their target directory, so `Scripts/sync-contracts.sh`
copies the spec to `Sources/CoreAPI/openapi.json` first. Config:

```yaml
generate: [types, client]
accessModifier: public
namingStrategy: idiomatic
```

Then verify the two agree:

```bash
python3 scripts/check_codegen_parity.py \
  --kotlin-models ../android/contract/generated/.../models \
  --swift-types   ../ios/.build/.../GeneratedSources/Types.swift
```

## Behavioural vectors

The OpenAPI contract makes the clients agree on wire format. It says nothing about *behaviour*, and
that is where divergence is invisible: two independent implementations of "round this portion ratio
to one decimal" fail no compiler and no test either team writes, and show the user two different
numbers.

`vectors/` closes that gap — 144 cases across 17 suites, each with an `input`, an `expected`, and a
`why` explaining the invariant it pins. All three clients assert against the same files.

The corpus is **generated from the sandbox's reference implementation**, which is the only place the
expected values are executed:

```bash
cd ../sandbox
npm run vectors:build     # rewrites vectors/ here
npm test                  # fails if vectors/ here is stale, or if behaviour has drifted
```

Two independent gates, because one of them cannot see the other's failure mode:

| gate | lives in | catches |
|---|---|---|
| `npm test` | sandbox CI | an `expected` value that no longer matches the implementation, and a stale `vectors/` here |
| "vectors/ is a well-formed behavioural corpus" | contracts CI | a malformed or internally inconsistent corpus, an `index.json` that has drifted from the files beside it, and loss of the rounding tie cases |

The single most important thing in there is the rounding rule: `floor(x + 0.5)`, half-up.
`kotlin.math.round` breaks ties **towards even**, so the obvious Kotlin port of `Math.round` silently
changes user-visible numbers. `vectors/README.md` has the details, and the porting rules a Kotlin or
Swift implementer needs.

## Design tokens

`pocket-nutrition/design/foundations/pocket-nutrition.css` is the source. `tokens/tokens.json`
mirrors it in DTCG form, and every value there appears **literally** in that stylesheet — verified
by cross-checking all 30 brand colours against it, so the mirror is a transcription rather than an
interpretation. `semantic-map.json` then records which token each UI role uses, read off the same
stylesheet's component rules; that is the part a porter cannot infer from a palette alone.

```bash
python3 scripts/emit_tokens.py            # write tokens/generated/
python3 scripts/emit_tokens.py --check    # CI: fails if the committed output is stale
```

The emitter is also the only place `semantic-map.json`'s token references get resolved, so a typo in
a dotted path fails there instead of becoming a transparent button in one app.

Two things worth knowing before using them:

- **The sandbox does not consume these tokens.** It uses raw Tailwind utilities, so the native apps
  are the first clients of the brand palette and will legitimately differ from the sandbox in colour.
- **`cooking-palette.json` is the one derived file.** Four methods map onto existing brand tokens by
  meaning (leaf=raw, sea=boiled, carrot=grilled, gold=roasted); `steamed` and `fried` have no brand
  token and were derived in OKLCH, with the tint and ink rules *measured* from the brand's own
  base/soft and base/ink pairs rather than eyeballed. Every label pairing clears WCAG AA 4.5:1 —
  which required inverting the label to dark on grilled and roasted, where white reaches only 3.0:1
  and 3.2:1. That file's `$extensions` carries the full derivation.

## French/English copy

`strings/fr.json` started as a verbatim French extraction from the sandbox. The sandbox itself
stays French-only and the spec requires identical French wording across clients, so `fr` is what a
porter copies from. Since contract 2.0.0, every `shared`/`app` entry also carries an `en` value,
hand-translated (not machine-translated) for the native apps' language switcher — the sandbox has
no English UI and never gets one.

Every entry carries a `scope`: `shared` (reproduce everywhere), `sandbox` (the usability-test welcome
screen and the API-gaps panel, which are researcher surfaces and must not ship in a product app), or
`app` (wording the native clients have and the prototype does not — the local food journal, the
about screen with its licence and attribution obligations, and the language switcher itself).
Currently **99 shared, 19 sandbox-only and 29 app-only**; CI prints the same numbers, plus an `en`
coverage check over the shared+app entries, on every run, so a stale count or a missing translation
is visible.

Two defects are **recorded rather than silently fixed**, because normalising copy is the design
owner's call: the sandbox mixes ASCII `'` with typographic `’`, and it uses two different emoji for
`boiled`. The palette resolves the emoji to one value (🫧); the apostrophes are still mixed and
flagged in `$extensions`.

## Consuming this repo

Each app repo **vendors** the artifacts rather than using a git submodule: a stale submodule
pointer is silent, which is the exact failure mode this repo exists to prevent.
`scripts/sync-contracts.sh --update` in each app refreshes from the pinned `CONTRACTS_VERSION`;
`--verify` runs in CI and fails on any diff.

## Out of scope

| Not here | Reason excluded |
|---|---|
| Runtime code | Consumers generate or implement their own; this repo ships data |
| API implementation | Lives in `pocket-nutrition/api`; this repo only mirrors its published contract |
| Design mockups | Live in `pocket-nutrition/design`; only machine-readable tokens are mirrored here |
| A build system | Deliberate. Committed outputs plus two scripts stay reviewable and work offline |

## Contributing

Backend and two mobile clients all vendor this repository at a pinned tag, so changes here need
more care than an ordinary PR. See [CONTRIBUTING.md](CONTRIBUTING.md) for how to run the two
`--check` scripts, what belongs in each directory, and which changes need approval first (also
see `AGENTS.md`). Found a stale vector, a stale spec snapshot, or a token that has drifted from
the stylesheet? Use the templates under `.github/ISSUE_TEMPLATE/`.

## Licence

MPL-2.0 — see `LICENSE`. This repository sits in the **client tier** of a two-tier platform:

| Tier | Licence | Repos |
|---|---|---|
| Backend — never distributed to end users | AGPL-3.0-or-later | `api`, `ml`, `ingest`, `community`, `data`, `knowledge` |
| Client chain — compiled into shipped app binaries | **MPL-2.0** | **`contracts`**, `android`, `ios` |

Run any part of the *backend* as a network service and AGPL-3.0 §13 still requires you to share
your modifications. That is the point, and it applies to a fork of the API just as much as to the
original. The client tier is weaker on purpose, and only as weak as it has to be: MPL-2.0 is
file-level copyleft, so a fork must publish its changes to **our** files and may only keep new
files of its own closed.

### What this means for mobile distribution

This repository is vendored *into* both app binaries (tokens, strings, vectors, generated model
code), so its licence is the binary's licence problem, not just its own.

AGPL-3.0 §10 forbids imposing "further restrictions" on the rights it grants, and §6 adds an
installation-information requirement. Apple's Licensed Application EULA imposes exactly such
restrictions — it limits users to devices they own, restricts sharing, and DRM-wraps the binary.
A copyright holder filed a DMCA notice against VLC for iOS on that ground in 2011 and Apple
removed it. Note the mechanism: Apple does not scan for copyleft, a **copyright holder complains**.

MPL-2.0 §3.3 explicitly permits distributing a "Larger Work" under other terms, including more
restrictive ones. That is the clause the GPL family lacks, and the reason Firefox for iOS and
Firefox Focus ship from the App Store under MPL-2.0 today.

| Channel | Status under MPL-2.0 |
|---|---|
| GitHub Releases (signed APK/AAB) | Fine — remains the primary channel |
| F-Droid | Fine |
| Google Play | Fine |
| Apple App Store / TestFlight | **Viable.** This is why the client tier is MPL-2.0 |
| iOS development / ad-hoc install | Fine |

**Never attach MPL-2.0 Exhibit B** ("Incompatible With Secondary Licenses") to a file in this
repository. Exhibit B would make this code un-combinable with GPL/LGPL/AGPL, and the AGPL `api`
consumes this contract. Exhibit A (`SPDX-License-Identifier: MPL-2.0`) is the header to use.

### Design tokens

`pocket-nutrition/design/foundations/pocket-nutrition.css` carries an explicit `MPL-2.0` header,
and so does this repo — both moved to the client tier together — so there is no licence friction
in mirroring token values into `tokens/tokens.json`. Tokens are still *generated* rather than
hand-ported, for the reason that has nothing to do with licensing: a copy-pasted hex value drifts,
and a generated one cannot.
